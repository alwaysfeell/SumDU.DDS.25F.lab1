# Single Points of Failure поточної архітектури

Варіант 5: Read-Heavy додаток. Близько 95 % операцій — читання, записи рідкісні, швидкість читання критична. Читання має працювати навіть при збої master, RTO для записів < 2 хв. Доступність читання важливіша за доступність запису. Бюджет 100–150 $/міс.

Поточний час відновлення — оцінка тривалості ручних дій без моніторингу (час, щоб помітити збій, плюс час на виправлення).

| --- | --- | --- | --- | --- | --- |
| 1 | Primary PostgreSQL (traveler_db) | застосунок працює лише з `db`, тому зупиняються і записи, і читання (перевірено: `/health` → 503, `GET /api/travel-plans` → 500). Репліка має всі дані, але не використовується | читання і запис: 10–30 хв | читання: без перерви; запис: < 2 хв | Критичний |

## Висновки

- Головний розрив для варіанта 5: репліка існує, але застосунок її не використовує. Читання, яке за вимогами має переживати збій master, повністю залежить від primary.
- Реплікація без автоматики і без маршрутизації дає лише копію даних, а не доступність.
- Синхронна реплікація з однією реплікою захищає дані, але робить репліку додатковою точкою відмови для записів.
- Усе розміщено на одному хості, тому навіть ідеальна автоматика всередині Docker не захищає від відмови комп'ютера, диска або Docker Engine.
- Без бекапів і архіву WAL логічна помилка або втрата диска означає втрату всіх даних.
