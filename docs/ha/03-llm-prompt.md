# Промпт для LLM

## Початковий промпт

Однаковий для всіх LLM, кожна модель – у новому чаті без попереднього контексту.

```text
Мене звати Владислав Косілов. Я магістрант (група ІН.м-62) і виконую роль системного архітектора свого навчального проєкту. Виступи, будь ласка, технічним консультантом з баз даних і надійності систем.
 
1. Застосунок
TravelerAPI — REST API для колаборативного планування подорожей: користувачі створюють плани подорожей і спільно додають до них локації. Стек: Python 3.15, FastAPI, Uvicorn (один процес), драйвер psycopg 3 з пулом з'єднань psycopg_pool (2–20 з'єднань). Конкурентні зміни контролюються оптимістичним блокуванням (поле version, UPDATE ... WHERE version = ...) і коротким SELECT ... FOR UPDATE, тому втрата вже підтверджених транзакцій для нас неприйнятна. Сервер застосунку не зберігає стан між запитами. Навантажувальні тести k6 показали: до 500 одночасних віртуальних користувачів без порушення вимог, близько 300 запитів/с, p95 < 10 мс при 300 користувачах; вузьке місце — застосунок, а не БД (БД завантажена до 16 % CPU).
 
2. Поточна архітектура
- Усе розгорнуто через Docker Compose на одному комп'ютері (Windows 11, Docker Desktop), одна bridge-мережа backend.
- Контейнер web — застосунок. Підключається до БД рядком DATABASE_URL з фіксованим ім'ям хоста db:5432.
- Контейнер db — основний сервер PostgreSQL 18.6 (образ postgres:18-alpine), приймає всі читання і записи.
- Контейнер db_replica — фізична потокова репліка (hot standby, лише читання), створена через pg_basebackup з фізичним слотом реплікації. Реплікація синхронна: synchronous_standby_names = 'FIRST 1 (replica1)', synchronous_commit = on. Застосунок до репліки не звертається.
- Кожен сервер PostgreSQL має власний Docker volume на тому самому диску.
- Ліміти ресурсів: web — 2 CPU / 512 MB, кожен PostgreSQL — 2 CPU / 1 GB.
- Безпека: порти опубліковано лише на 127.0.0.1, pg_hba.conf дозволяє підключення лише з мережі контейнерів методом scram-sha-256, паролі зберігаються в .env.
- Немає моніторингу, сповіщень, резервного копіювання і жодних інших компонентів між застосунком і БД. Будь-які дії після збою зараз виконуються вручну.
 
3. Бізнес-вимоги (read-heavy сценарій)
- близько 95 % операцій — читання (перегляд планів подорожей і локацій), записи рідкісні; швидкість читання критична;
- читання має працювати навіть при збої основного сервера БД;
- RTO для записів < 2 хвилин;
- доступність читання важливіша за доступність запису;
- бюджет на інфраструктуру 100–150 $ на місяць; систему можна перенести з одного комп'ютера на кілька віртуальних машин у хмарі;
- проєкт розробляю і підтримую я сам, досвід адміністрування PostgreSQL середній, тому рішення має бути посильним для однієї людини.
 
4. Мої запитання
1) Проаналізуй поточну архітектуру: які в ній слабкі місця з погляду надійності і що станеться при збої кожного компонента?
2) Які існують підходи, щоб база даних автоматично виявляла збій і відновлювалась без участі людини? Як при цьому застосунок дізнається, куди підключатися?
3) Що ти порекомендуєш саме для мого випадку? Назви конкретні інструменти, кількість серверів і як розмістити компоненти. Чи вкладається рішення у вимоги до читання, RTO для записів і бюджет?
4) Які проблеми, ризики й обмеження має рекомендоване рішення і як їх зменшити?
5) За якими критеріями варто порівнювати можливі варіанти?
Якщо тобі бракує інформації, постав уточнювальні запитання.
```
